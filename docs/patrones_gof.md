# Patrones GOF - Sistema Fitness

## Introducción

Este documento presenta el análisis conceptual de los 23 patrones de diseño GOF (Gang of Four), clasificándolos según su categoría, problema que resuelven, estructura básica, ventajas, desventajas, relaciones y posibles casos de uso dentro del desarrollo de software orientado a objetos.

El objetivo de esta documentación es servir como apoyo conceptual para la implementación práctica de patrones GOF aplicada al sistema fitness desarrollado durante la actividad académica.

---

# Tabla de Patrones GOF

| Patrón | Categoría | Problema que Resuelve | Estructura Básica | Casos de Uso | Ventajas | Desventajas | Patrones Relacionados |
|---|---|---|---|---|---|---|---|
| Abstract Factory | Creacional | Permite crear familias de objetos relacionados sin depender de clases concretas. | Cliente → Fábrica Abstracta → Productos Concretos | Sistemas con múltiples familias de objetos relacionadas, interfaces gráficas multiplataforma, creación desacoplada de componentes. | Reduce el acoplamiento, favorece la extensibilidad y consistencia entre productos. | Aumenta complejidad estructural y número de clases. | Factory Method, Builder, Singleton |
| Builder | Creacional | Permite la construción de objetos complejos paso a paso separando el proceso de construcción de la representación final. | Director → Builder → Producto | Construcción de objetos complejos, generación de configuraciones personalizadas, creación modular de estructuras. | Mejora legibilidad, desacopla construcción y facilita reutilización. | Puede aumentar la cantidad de clases y dificultad estructural. | Abstract Factory, Factory Method, Composite |
| Factory Method | Creacional | Define una interfaz para crear objetos permitiendo que las subclases decidan qué clase concreta instanciar. | Creador → Factory Method → Producto Concreto | Sistemas con múltiples tipos de objetos relacionados, creación desacoplada de componentes, frameworks extensibles. | Disminuye el acoplamiento, facilita extensión y centraliza la creación de objetos. | Puede aumentar la dificultad y cantidad de subclases. | Abstract Factory, Builder, Prototype |
| Prototype | Creacional | Permite la creación de nuevos objetos clonando instancias existentes en lugar de crearlos desde cero. | Prototipo → Clonación → Nuevo Objeto | Sistemas donde la creación de objetos es costosa, generación dinámica de configuraciones, duplicación eficiente de estructuras complejas. | Reduce costos de creación, mejora el rendimiento y evita dependencias directas con clases concretas. | La clonación compleja puede complicar la implementación y mantenimiento. | Factory Method, Abstract Factory, Singleton |
| Singleton | Creacional | Garantiza que una clase tenga una única instancia y proporciona un punto global de acceso a ella. | Cliente → Singleton → Instancia Única | Configuraciones globales, manejo de recursos compartidos, control centralizado del sistema. | Controla acceso global, evita múltiples instancias y optimiza recursos compartidos. | Puede generar alto acoplamiento y dificultar pruebas unitarias si se usa incorrectamente. | Abstract Factory, Facade, Prototype |
| Adapter | Estructural | Permite que clases con interfaces incompatibles puedan trabajar juntas mediante una adaptación intermedia. | Cliente → Adapter → Servicio Adaptado | Integración de sistemas heredados, compatibilidad entre librerías, reutilización de componentes incompatibles. | Favorece la reutilización y compatibilidad sin modificar el código existente. | Puede incrementar dificultad y añadir capas adicionales al sistema. | Facade, Bridge, Decorator |
| Bridge | Estructural | Separa una abstracción de su implementación permitiendo que ambas evolucionen independientemente. | Abstracción → Implementación → Implementación Concreta | Sistemas con múltiples variantes funcionales, plataformas independientes, desacoplamiento de capas complejas. | Reduce el acoplamiento, mejora extensibilidad y favorece la composición sobre herencia. | Puede incrementar dificultad estructural inicial. | Adapter, Strategy, Abstract Factory |
| Composite | Estructural | Permite tratar objetos individuales y composiciones de objetos de manera uniforme mediante estructuras jerárquicas. | Componente → Hoja / Composite | Estructuras en árbol, sistemas jerárquicos, menús, carpetas, interfaces gráficas complejas. | Simplifica el manejo de estructuras jerárquicas y favorece la reutilización. | Puede dificultar restricciones específicas sobre algunos componentes. | Builder, Decorator, Iterator |
| Decorator | Estructural | Permite añadir funcionalidades adicionales a un objeto dinámicamente sin modificar su estructura original. | Componente → Decorator → Decorador Concreto | Sistemas extensibles, funcionalidades dinámicas, personalización modular de objetos. | Favorece la composición sobre herencia y permite extensibilidad flexible. | Puede aumentar la dificultad y cantidad de objetos en el sistema. | Composite, Adapter, Strategy |
| Facade | Estructural | Proporciona una interfaz simplificada para la interacción con subsistemas complejos. | Cliente → Facade → Subsistemas | Sistemas con múltiples módulos internos, simplificación de APIs, centralización de acceso a funcionalidades. | Reduce la complejidad, mejora organización y disminuye acoplamiento entre componentes. | Puede volverse en una clase demasiado centralizada si se abusa del patrón. | Singleton, Adapter, Mediator |
| Flyweight | Estructural | Permite compartir objetos para disminuir el consumo de memoria en sistemas con gran cantidad de instancias similares. | Cliente → Flyweight Factory → Flyweight Compartido | Videojuegos, editores gráficos, sistemas con objetos repetitivos, optimización de recursos. | Reduce uso de memoria y mejora la eficiencia en grandes volúmenes de objetos. | Aumenta complejidad y necesita separar estados internos y externos. | Singleton, Factory Method, Composite |
| Proxy | Estructural | Proporciona un objeto intermediario que controla el acceso a otro objeto. | Cliente → Proxy → Objeto Real | Control de acceso, carga diferida, seguridad, acceso remoto y optimización de recursos. | Permite rl controlar acceso, optimizar rendimiento y añadir seguridad sin cambiar el objeto real. | Puede aumentar complejidad y añadir niveles adicionales de indirección. | Decorator, Adapter, Facade |
| Chain of Responsibility | Comportamiento | Permite pasar solicitudes a través de una cadena de objetos hasta que alguno pueda procesarla. | Cliente → Handler → Handler Concreto | Sistemas de validación, middleware, procesamiento de eventos y flujos de autorización. | Disminuye acoplamiento entre emisor y receptor y permite cadenas flexibles de procesamiento. | Puede dificultar el seguimiento del flujo y generar cadenas complejas. | Command, Mediator, Observer |
| Command | Comportamiento | Encapsula una solicitud como un objeto permitiendo parametrizar operaciones y desacoplar emisores de receptores. | Cliente → Command → Receiver | Sistemas de acciones, menús, colas de tareas, deshacer/rehacer operaciones y automatización de procesos. | Reduce acoplamiento, facilita extensibilidad y permite registrar operaciones. | Puede aumentar la cantidad de clases y complejidad del sistema. | Chain of Responsibility, Mediator, Strategy |
| Interpreter | Comportamiento | Define una representación para una gramática y proporciona un mecanismo para la interpretación de expresiones del lenguaje. | Contexto → Expresión → Interpretación | Lenguajes de consulta, expresiones matemáticas, compiladores, validadores y procesamiento de reglas. | Facilita extensión de gramáticas y organización de reglas de interpretación. | Puede generar arquitecturas complejas y difíciles de mantener en gramáticas grandes. | Composite, Visitor, Command |
| Iterator | Comportamiento | Permite recorrer elementos de una colección sin exponer su estructura interna. | Cliente → Iterator → Colección | Recorrido de listas, árboles, colecciones de datos y estructuras complejas. | Simplifica recorridos, desacopla iteración y favorece encapsulamiento. | Puede aumentar complejidad en colecciones simples. | Composite, Visitor, Factory Method |
| Mediator | Comportamiento | Centraliza la comunicación entre objetos evitando dependencias directas entre ellos. | Colegas → Mediator → Comunicación Centralizada | Interfaces gráficas, sistemas de mensajería, coordinación de módulos y flujos complejos de interacción. | Reduce el acoplamiento y centraliza la lógica de interacción entre componentes. | El mediador puede volverse en una clase compleja y difícil de mantener. | Observer, Command, Facade |
| Memento | Comportamiento | Permite guardar y restaurar el estado interno de un objeto sin violar el encapsulamiento. | Originador → Memento → Caretaker | Sistemas de deshacer/rehacer, recuperación de estados, historiales y restauración de sesiones. | Facilita recuperación de estados y mantiene encapsulamiento del objeto original. | Puede aumentar consumo de memoria al almacenar múltiples estados. | Command, Iterator, State |
| Observer | Comportamiento | Define una dependencia uno a muchos entre objetos para notificar automáticamente cambios de estado. | Subject → Observer → Notificación | Sistemas de eventos, notificaciones, interfaces gráficas y arquitecturas reactivas. | Reduce el acoplamiento y facilita actualización automática entre componentes. | Puede generar múltiples notificaciones y comportamientos difíciles de rastrear. | Mediator, State, Publish-Subscribe |
| State | Comportamiento | Permite que un objeto modifique su comportamiento cuando cambia su estado interno. | Contexto → Estado → Estado Concreto | Máquinas de estados, flujos de procesos, interfaces dinámicas y sistemas con múltiples comportamientos dependientes del estado. | Elimina las condicionales complejos y mejora la organización del comportamiento. | Puede aumentar la cantidad de clases y dificultad del diseño. | Strategy, Observer, Singleton |
| Strategy | Comportamiento | Define una familia de algoritmos encapsulándolos e intercambiándolos dinámicamente en tiempo de ejecución. | Contexto → Strategy → Estrategia Concreta | Sistemas con múltiples algoritmos, recomendaciones dinámicas, métodos de pago, validaciones y comportamientos configurables. | Disminuye condicionales, favorece extensibilidad y facilita reutilización de algoritmos. | Puede aumentar la cantidad de clases y complejidad estructural. | State, Command, Template Method |
| Template Method | Comportamiento | Define la estructura general de un algoritmo permitiendo que las subclases redefinan pasos específicos sin alterar el flujo principal. | Clase Abstracta → Template Method → Subclase | Frameworks, procesamiento de datos, flujos empresariales y algoritmos reutilizables. | Favorece reutilización y control estructurado de algoritmos. | Puede generar dependencia fuerte a través herencia. | Strategy, Factory Method, State |
| Visitor | Comportamiento | Permite definir nuevas operaciones sobre una estructura de objetos sin modificar sus clases. | Visitor → Elemento → Visita Concreta | Compiladores, análisis de estructuras, procesamiento de árboles y operaciones complejas sobre colecciones de objetos. | Facilita añadir nuevas operaciones y separa comportamiento de la estructura de datos. | Puede dificultar agregar nuevos tipos de elementos y aumentar complejidad. | Composite, Iterator, Interpreter |

# Conclusión

El análisis de los 23 patrones de diseño GOF permitió comprender cómo diferentes soluciones arquitectónicas pueden aplicarse para resolver problemas comunes dentro del desarrollo de software orientado a objetos. A través de esta documentación se identificaron las principales características, ventajas, desventajas, relaciones y escenarios de aplicación de cada patrón, permitiendo fortalecer conceptos relacionados con modularidad, reutilización, desacoplamiento y mantenibilidad del software.

A su vez, el desarrollo conceptual realizado sirvió como base para la construcción de la arquitectura del sistema fitness propuesto, facilitando posteriormente la implementación práctica de los patrones Builder, Factory Method, Singleton, Decorator, Strategy, Facade y Command dentro del proyecto desarrollado en Python.

Durante el proceso se aplicaron principios SOLID, composición sobre herencia, encapsulamiento y buenas prácticas de ingeniería de software, buscando mantener una solución organizada, escalable y alineada con estándares de diseño modernos. Finalmente, esta actividad permitió fortalecer tanto las habilidades de modelado arquitectónico como la capacidad de relacionar teoría y práctica dentro del desarrollo de software orientado a objetos.
